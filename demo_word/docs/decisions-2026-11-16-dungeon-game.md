# 地下城游戏实现 — 执行裁决记录

- 日期：2026-11-16
- 计划：`docs/superpowers/plans/2026-11-16-dungeon-game.md`
- 规格（权威）：`docs/superpowers/specs/2026-11-16-dungeon-game-design.md`
- 背景：执行期间用户授权「后面有决策按你的来」，本文档记录执行者（控制器）代用户作出的每一条裁决。每条含：**决定 / 理由 / 如果错了的代价**。用户可逐条否决并返工。
- 规则：计划原文与规格冲突时以规格为准；两者都未规定处由执行者裁定并记录于此。

## 裁决清单（按作出顺序）

### C22 — 饰品智力加成如何生效
- **决定**：核心导出 `totalIntel(player) = intel + (equipment.trinket?.intel || 0)`；探索判定与面板一律使用总智力。
- **理由**：规格 7.5 明确饰品「+智力」，但计划只定义了 `totalAtk`/`totalDef`，智力加成若无入口则静默失效。
- **代价**：若不应计入探索判定，则探索成功率被轻微高估——只影响平衡，不影响正确性。

### C26 — 场景/怪物文案放哪层
- **决定**：每层场景（emoji/CSS 渐变/房间文案）与怪物描述文案放在 `game-ui.js`（SCENES、MONSTER_DESCS 表），核心 `game-logic.js` 只留数据。
- **理由**：规格 7.8 允许建造者用 CSS+emoji 营造场景；文案属表现层，混入核心会让纯函数文件承担展示职责。
- **代价**：文案与数据分置两处，后续改怪物需要同时改两个文件。

### C25 — UI 选项的接线时机
- **决定**：任务 5 的楼层选项按钮为 inert（不绑点击），任务 5 只接线角色选择；任务 6/7 负责挂 handler。
- **理由**：探索/战斗逻辑在任务 6/7 才存在，任务 5 若先绑占位 handler 会留下易被遗忘的假行为。
- **代价**：任务 6/7 审查时需确认所有选项都已接线。

### C27 — 任务 6 触发怪物时的中转
- **决定**：怪物遭遇统一经 `enterEncounter()` 进入；任务 6 实现时若 `startBattle`（任务 7）尚未定义则记占位日志并重新给出选项，任务 7 补全。
- **理由**：任务 6 先于任务 7 落地，直接引用未定义函数会在验证时崩溃。
- **代价**：任务 7 必须记得替换占位路径，否则探索失败永远不会进入战斗（任务 7 审查会盯这一点）。

### C5 — 胜利后不重复回血
- **决定**：UI 胜利流只调用 `advanceFloor`（其内部已含 25% 回血），不再单独调 `healOnNewFloor`。
- **理由**：计划 T7 文本「advanceFloor + healOnNewFloor」会双重回血（50% 而非规格 7.10 的 25%）。
- **代价**：无——这是修正计划文本的冗余，规格明确每层回 25%。

### C28 — 第 20 层胜利流顺序
- **决定**：击败怪物 = `endCombat`（回满法力）→ `rollReward`（必得掉落）→ 若 `floor===20` 出「复苏之心」胜利结局；否则 `advanceFloor` 进入下一层。
- **理由**：规格 7.4 打败怪物必得奖励；7.7 第 20 层打败 Boss 即胜利结束，不应再推进楼层。
- **代价**：第 20 层 Boss 的掉落不生效（按规格这局已结束，属预期）。

### C18 — 战斗内自由输入
- **决定**：自由输入是全局机制（任务 6 建，任务 7 战斗视图同样保留）；战斗内关键词映射到普攻与四个技能，未识别输入用计划逐字兜底文案。
- **理由**：规格 7.9 与源规则要求每步都有「说出你想做什么」，战斗回合同理。
- **代价**：战斗内关键词误命中（如「打」也匹配其他词）可能选错技能——兜底文案会兜住其余情况。

### C30 — 构建内联方式
- **决定**：`build.mjs` 用正则匹配 `<link rel="stylesheet" href="…">` 与 `<script src="…">` 并逐文件读盘内联，不做整串精确匹配。
- **理由**：精确字符串匹配对空白/属性顺序脆弱，正则对 index.html 的小改动更稳。
- **代价**：若 index.html 出现非常规写法（如带 `integrity` 属性的外链）正则可能漏配——但本项目零外链，不存在此场景。

### C29 — 子代理无法手测的替代验证
- **决定**：任务 8 的「全流程手测」以四件事替代：(a) `node --test tests/` 全套通过；(b) 构建后 grep `dist/index.html` 确认零外链；(c) headless Edge（`msedge --headless --dump-dom`）冒烟（如可用）；(d) headless Node 全流程模拟——固定种子 rng 驱动核心逻辑跑满 20 层，两个角色都验证可通关。真人浏览器手测保留为用户侧最后一步。
- **理由**：子代理没有真人手；规格 9 的「能玩能跑」需要可重复的证据，模拟比口头声明强。
- **代价**：模拟只覆盖核心逻辑路径，不覆盖 UI 交互细节（按钮可用性、滚动、移动端排版）——这部分仍需用户在真实浏览器里确认。

### C8 — rollExploration 的 rng 调用顺序
- **决定**：`rollExploration(intel, rng)` 按序调 rng 两次：先 `difficulty = 9 + Math.floor(rng()*5)`，后 `roll = 1 + Math.floor(rng()*6)`。
- **理由**：计划未钉顺序，固定 rng 测试需要确定行为；「先定难度再掷骰」符合规格 7.3 的叙述顺序。
- **代价**：若测试用例按相反顺序写固定值，会不一致——任务 1 的测试以简报逐字文本为准，实现必须服从测试。

### C1 — 测试玩家对象缺字段的守卫
- **决定**：法力检查/扣减、HP 扣减都用 `typeof x === 'number'` 守卫，缺字段不崩溃。
- **理由**：计划 T2 的部分测试玩家对象故意不带 `mana`/`hp`，实现若直接运算会产生 NaN 或抛错。
- **代价**：守卫掩盖了真实对局中「缺字段」本应暴露的 bug——但 `newGame` 保证真实状态永远带全字段，守卫只在测试边缘生效。

### C2 — 护甲加成的入口
- **决定**：T2 的 `monsterTurn` 内联 `def + (equipment.armor?.def || 0)`；T3 导出 `totalDef` 同式；UI 面板用 `GL.totalDef`。
- **理由**：计划自述 `totalDef` 在 T3 定义，但 T2 的怪物回合就需要含护甲的防御值。
- **代价**：同一公式出现两处，改公式要改两处（最终审查可提示合并）。

### C19 — SKILLS 键的大小写
- **决定**：`SKILLS` 导出用小写键 `mage`/`warrior`，与 `CHARS` 键和 `charType` 对齐。
- **理由**：计划 T7 用 `GameLogic.SKILLS[charType]`，若键是大写 `MAGE` 则为 undefined，战斗选项渲染直接失败。
- **代价**：无——只是把计划表头的大写标签与运行时键区分开。

### C6 — 裁决失败的法力消耗
- **决定**：战士「裁决」对 HP≥20% 的敌人失败时仍消耗 30 法力，无其他效果。
- **理由**：计划原文「视为无效回合，不消耗以外的效果」——消耗照旧，效果为零。
- **代价**：玩家可能觉得「白耗法力」不公平——这是计划的字面语义。

### C7 — 奥术智慧回法上限
- **决定**：奥术智慧 +30 法力以 `maxMana` 为上限。
- **理由**：法力值全局都有上限约束，超限无意义。
- **代价**：无。

### C20 — rollReward 返回结构
- **决定**：属性成长 `{type:'stat', kind, amount}`；装备 `{type:'equipment', slot, name, atk?/def?/intel?/manaRegen?}`；UI 按 `type` 路由到 `applyStatReward`/`applyEquipment`。
- **理由**：计划只说「返回属性成长或装备对象」，没给判别字段，UI 无法路由。
- **代价**：无——这是补充未定义的结构，不改变任何数值。

### C21 — 饰品「回法」语义
- **决定**：饰品带 `manaRegen`（取值 5）；每次 `advanceFloor` 进入新层时回复该值法力（上限封顶）。
- **理由**：规格 7.5「饰品（+智力或回法）」+ 计划「每层回法」，按层生效是唯一自洽读法。
- **代价**：若应改为每回合回法，法师/战士后期法力经济会偏松——只影响平衡。

### C23 — 同槽装备平局
- **决定**：同槽新装备严格更高才替换；同值丢弃。
- **理由**：计划「数值更高则替换，否则丢弃」——「否则」包含平局。
- **代价**：玩家可能期望平局替换（换名字）——无功能影响。

### C24 — 每层回血取整
- **决定**：`healAmount = Math.floor(maxHp * 0.25)`，HP 保持整数。
- **理由**：HP 上限奖励后 maxHp 可为 130，25% = 32.5 会引入小数 HP。
- **代价**：无（130→32 与 32.5 的差异可忽略）。

### C14 — 祭坛双模式
- **决定**：`healAltar(player, rng, mode='pray')`；`pray` = 法力 +30（封顶）；`risk` = 50/50 大奖励（rollReward）或 10~20 伤害。
- **理由**：规格 7.6「祈祷回法力，或冒风险换大奖励」是两个 UI 选项，但计划签名没有模式参数。
- **代价**：若大奖励期望值低于 10~20 伤害的风险，「冒险」选项恒劣——奖励侧用 rollReward 保底，风险对称可接受。

### C3 — 必遇怪的触发计数
- **决定**：`shouldEncounter(state, exploredCount) = exploredCount >= 1`；UI 允许第 2 次探索，`exploredCount >= 2` 后隐藏探索选项、强制遭遇。
- **理由**：测试钉死 `shouldEncounter(1)===true`，而规格 7.7 说「1-2 次探索后必遇怪」——函数管「遭遇变为必选」，UI 管「给几次探索」。
- **代价**：若玩家一直点第 2 次探索，遭遇最多推迟一步——符合「1-2 次」措辞。

### C9 — getFloorContent 的 rng 可选与缓存
- **决定**：`getFloorContent(floor, rng = Math.random)`；UI 按层缓存结果，重渲染不重抽。
- **理由**：T4 测试不传 rng 调用该函数；若每次渲染重抽，玩家看到的选项会漂移。
- **代价**：无。

### C10 — 箱子陷阱
- **决定**：20% 概率陷阱（5~10 伤害），否则获得 `rollReward` 奖励。
- **理由**：规格 7.6「小概率是陷阱（小伤害）」——数值留给建造者。
- **代价**：概率/伤害取值只是平衡手感，无正确性影响。

### C11 — 谜题机关
- **决定**：二选一判定，50/50；成功得奖励，失败 5~10 伤害。
- **理由**：规格 7.6「简单判定，如二选一或数字题」+「失败少量伤害」。
- **代价**：同上，仅平衡。

### C12 — 猜拳石像
- **决定**：怪物出招 `1+Math.floor(rng()*3)`；赢得奖励，输 5~10 伤害，平局无事；元素均消耗。
- **理由**：规格 7.6「赢奖励、输小惩罚」；平局规格未提，无事发生最自然。
- **代价**：无。

### C13 — 陷阱通道
- **决定**：直接通过 30% 概率 5~10 伤害、必通过；「先探查」走探索判定，成功安全通过、失败受伤但通过。
- **理由**：规格 7.6「小概率触发伤害，可提前探查规避」——探查不能 100% 规避（否则探索判定无风险），失败仍通过符合「通道」语义。
- **代价**：若期望探查成功=绝对安全且失败=不通过，行为会不同——只影响流程手感。

### C15 — 探索失败的惩罚
- **决定**：50/50——5~10 伤害，或立即触发怪物遭遇。
- **理由**：规格 7.3「惩罚：少量伤害，或触发一个怪物」——「或」由 DM（此处为程序）随机择一。
- **代价**：无。

### C16 — 探索成功的奖励
- **决定**：必得 `healExploreSuccess`（+10~15 HP），另 50% 概率追加 `rollReward`。
- **理由**：规格 7.3 成功奖励「小量 HP/法力，或装备/属性」——回血是保底，装备/属性是追加；怪物掉落保持「必得」的特殊性。
- **代价**：若期望每次成功都掉装备，前期成长会更快——只影响平衡。

### C4 — 互动判定的代码归属
- **决定**：箱/谜题/猜拳/陷阱通道/探索失败的判定全部是 `game-logic.js` 的纯函数（rng 注入 + 单元测试）；UI 只调用、不内联概率。
- **理由**：规格 9 要求核心数值逻辑可测试；概率写在 UI 里就失去单测能力。
- **代价**：核心文件多几个小函数——这是计划「UI 只调用 GameLogic」的既定架构。

### C17 — 「走」关键词与必遇怪
- **决定**：自由输入「走」仅在本层怪物已击败时才进入下一层，否则回应「怪物仍在」。兜底文案逐字：「（这里没有能这样做的。请选择上方编号选项，或换个说法。）」
- **理由**：规格 7.7 必遇怪——「走」不能绕过战斗。
- **代价**：玩家若不理解为何走不了，兜底文案会提示选择编号选项。

### C31 — 提交卫生（所有任务）
- **决定**：git 从仓库根执行；每次只暂存任务清单列出的 `demo_word/…` 文件；commit 信息用计划逐字文本 + `Co-Authored-By: Claude Code <noreply@anthropic.com>`；绝不动其他项目目录。
- **理由**：monorepo 中 cal/farmer/snake_game 是已跟踪的他人项目，误暂存会污染提交。
- **代价**：无。

## 观察项（未裁决，待证据）

- **平衡性**：规格 7.10 要求「正常发挥可通关 20 层」并授权调平衡，但计划钉死了 20 个怪物的精确数值（如第 10 层 hp230/攻25/技50）。任务 8 的 headless 全流程模拟会给出证据；若某角色正常打法无法通关，届时再裁决（倾向温和软化曲线，保留名称与 HP 比例）。

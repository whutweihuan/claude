# warrior_web 设计文档：杀戮尖塔铁甲战士 · 网页复刻（个人研究）

日期：2026-11-13
状态：待批准（内容范围已由用户裁定 = **A：仅铁甲战士**）
上游决策来源：本仓库 `warrior/`（Tkinter 垂直切片，28 卡，已验证机制设计）；路线 B（TS 网页新实现，带走设计不带走代码）由用户选定。

## 1. 意图与缘由

用 AI 辅助把杀戮尖塔（Slay the Spire）铁甲战士的完整核心体验复刻到网页端，作为"AI 驱动的游戏移植/复刻工作流"研究课题。前作 warrior 已经证明：机制内核可以由 AI 高质量完成、内容数据化是成本控制的关键、GUI 返工是 token 消耗大头。本项目在此基础上验证两点：

1. 网页技术栈下，AI 对 UI 的自验证能力（截图 + DOM 断言）能否显著压低返工成本；
2. "机制审计 → 词汇表扩容 → 批量灌表 → 模拟校准"的内容管线能否把单卡边际成本压到接近常数。

研究性质决定了交付物是**完整过程 + 可玩游戏**，不是可发布商品。

## 2. 目标

- 浏览器中完整可玩：铁甲战士，三幕地图，击败第三幕 Boss 为胜；一局内可重开、可换种子。
- 内容范围（**用户裁定 = A：仅铁甲战士**）：最初口头范围"铁甲战士 338 张"经 wiki 实测核查为**全游戏口径误记**——铁甲战士常规卡池 72 张（普通 20/ uncommon 36/ rare 16，含升级形态约 144 条），全站卡牌页共 368 个（四职业+无色+诅咒+状态）。本项目复刻范围：这 72 张×升级 + 三幕全部怪物/Boss + 通用与铁甲相关遗物 + 支撑单局循环的事件/商店/火堆/宝箱 + 相关无色/诅咒/状态牌。数值以 wiki 公开数据为基线（具体补丁版本由 P0 审计确定并全文档统一）。B=全角色（$500–1200）、C=StS2 基线两个备选在检查环节被排除，理由存档于 §7/§8。
- 机制忠实度：伤害公式结算顺序、意图提前锁定、牌堆操作、关键词与状态牌管线，行为与所选基线版本一致。范围 A 实际需要的关键词为消耗（Exhaust）、X 费、连击（Combo）与状态牌；姿态等为范围 B 专属（见 §5.3 更正）。
- 可复现：任意种子 + 任意操作序列可重放；整局自动模拟可作为回归测试。
- 数值可信：自动对战 bot（启发式策略即可，强度不设验收门）跑 ≥1000 局产出胜率/死因/深度分布**参考**报表，报表离群触发定点复核。

## 3. 非目标与反目标

**非目标**（本期不做，未来可选）：
- 其他角色（静默猎手/故障机器人/观者）——范围 B 裁定则移出本节、新开设计；进阶 1-20、每日挑战、多人、mod 系统、云存档、移动端适配。

**反目标**（技术上可行也视为失败）：
- 使用原作任何美术、音频素材（连参考抠图都不做）；打包分发、上线公网。原作卡名/风味文本仅限本地研究使用，界面文案在照抄与重写之间取"中文社区惯用译名 + 自写简短描述"，不整段复制官方本地化文本。
- 用 canvas 游戏引擎画整套卡牌 UI（本项目 UI 本质是 DOM 强项，引擎动画是后期增强不是地基）。
- 为"像原作"引入任何后端服务。
- 把 warrior 的 Python 代码逐行翻译过来（那是双份债：既有 Tkinter 时代妥协，又要过语言关）。

## 4. 约束

- 纯前端：无后端、无构建期网络依赖（数据在仓库内），`npm run dev` 即玩，`npm run build` 出静态产物。
- 技术栈（本条为建造者决定，理由见 §5）：Vite + TypeScript(strict) + React 18；测试 Vitest（逻辑）+ Playwright（UI 截图与断言）；随机数注入 `mulberry32`（种子可复现，继承 warrior 验证过的做法）。
- 存档安全继承本仓库 `.claude/CLAUDE.md` 规则：读档时"不存在/损坏/暂时读不到"三分处理，I/O 错误不得触发新局覆盖；localStorage 写入全量 JSON、写前校验。
- Windows 环境；UI 自动化验收必须走真实启动路径（dev server + 真实浏览器），吸取 warrior 的 DPI 教训——不在测试进程里"模拟"渲染环境。
- Git 卫生：只提交本目录；`node_modules/`、`dist/`、`test-results/` 进 `.gitignore`。

## 5. 架构

### 5.1 分层

```
src/engine/    纯逻辑状态机：零 DOM、零 React、零随机全局态。所有公开动作
               （playCard/endTurn/moveToNode/...）返回 GameEvent[]
src/data/      content.json（卡牌/遗物/敌人/事件表）+ zod schema + validate()
src/ui/        React：只消费 EngineState 快照 + 派发 action；事件流→动画队列
src/sim/       无头整局模拟器 + 自动对战 bot + 报表脚本
scripts/       wiki 数据规范化、内容校验、模拟入口
```

### 5.2 从 warrior 带走的设计（已验证）

- **效果原语封闭集 + 未知即抛错**（warrior `apply_effect` 模式），配 `validate_content` 全表校验；审计确认基线约需 18 → 60~75 个原语。
- **遗物钩子**：warrior 的 `merged_mods` 静态聚合只够数值型词条；本项目升级为**钩子总线**——`onTurnStart/onTurnEnd/onCardPlayed/onExhaust/onDamageReceived/onHeal/onPotionUsed/onRest/onBattleStart/...`，遗物、卡持续效果、敌人被动注册到同一总线（这是承接原作触发型遗物体系的必要条件，见 §5.4）。
- **意图提前锁定 `pending_move`**、`layer_tier` 式遭遇缩放、奖励待领取队列（`pending` 机制）、事件选项预检（不允许把玩家坑进致死/负金币）、商店折扣从词条聚合来。
- **rng 全程注入**：整局模拟、种子复现、平衡报表全部依赖它。
- **三套封闭解释器分离**：战斗原语、遗物/卡钩子、事件原语，互不混用。

### 5.3 本项目升级的设计

- **删除装备槽（建造者决定）**：原作铁甲战士没有武器/防具系统。warrior 的装备词条、宝箱/商店装备位、火堆"打磨武器"全部不移植，忠实原作优先；火堆"锻造"保留为卡牌升级（原作有）。词条聚合与钩子模式继续服务于遗物。
- **结构化事件流取代日志行**：引擎返回 `GameEvent[]`（`{type:'damage', target, amount, absorbed, source}` 等），文案渲染、数字动画、战斗日志、模拟报表都是它的消费者。这是对 warrior 最大的单点改造。
- **卡牌实例化**：手牌元素是对象（`uid, id, upgraded, costMod, tempMods`），支撑 D6 改费、克隆（Anger）、临时卡等。
- **姿态系统 [仅范围 B 生效]**：愤怒/平静/神圣/虚无是**观者专属机制**，铁甲战士没有姿态卡（初稿曾误记，已由建造者检查纠正）。范围 A 下整条移出词汇表；范围 B 下实现 `stance` 状态 + 切换钩子与惩罚结算。
- **牌堆操作原语族**：置顶/置底/洗入/复制/从弃牌堆取回/修改手牌。
- **状态牌与诅咒**：不可打出、触发惩罚（Burn 回合末伤等），进入抽牌/洗牌管线。
- **敌人 Move 词汇扩展**：成长（Ritual）、回合末甲（Metallicize）、免疫驱散、向玩家牌堆塞牌、固定连招组合、召唤、多阶段（含 Boss 半血/阈值形态）。
- **关键词标记**：以卡的声明属性表达（范围 A 实际用到：exhaust、unplayable、X 费、combo），由抽/弃/回合边界管线统一处理，不写进每张卡的 effect；retain/innate/ethereal 等其余关键词按范围裁定进入词汇表。

### 5.4 内容生产管线（研究课题的真正主角）

1. **P0 机制审计**（先于一切引擎编码）：把范围内卡牌×升级、遗物、敌人逐条映射到候选原语/钩子集（范围 A 为 72 基础卡；范围 B 为全角色池），产出 `docs/audit/primitive-spec.md`（最终词汇表）+ 残差清单（表达不出的一小撮，逐个设计新原语或裁定特例）。验收：残差清单为空或每项有明确处置。
2. **数据规范化**：`scripts/` 从 wiki 抓表 → `content.json`（基线版本钉死于文档），字段含中文惯用名、数值、升级差异、关键词、目标语义。
3. **批量灌入**：内容表 + 每卡自动化冒烟（bot 无脑打出全卡池不崩、校验器全绿），可按批次并行推进。
4. **模拟校准**：bot 报表异常（某卡胜率离群）→ 定点复核实现与数据。

## 6. 里程碑与验收门

每个里程碑独立可合并；**验收命令写进计划，跑绿才算完成**。

- **M1 引擎骨架 + 最小战斗**：分层目录、事件流、卡实例、10~15 张 act1 代表卡（含 2~3 张机制边缘卡压测引擎：X 费如 Offering/Fiend Fire、连击 Double Tap、自伤抽牌 Bloodletting）、2 种怪、完整回合循环；Playwright 战斗屏截图验收（无裁切/可点出牌）。*第一个真金白银的验证点：网页栈 UI 自验证闭环是否成立。*
- **M2 机制词汇表全量**：钩子总线、状态牌、牌堆操作、关键词——primitive-spec 的全部词汇落地并各有单测（范围 B 追加姿态/星球/印记等职业专属词汇）。
- **M3 全卡池灌表**：范围内卡牌×升级进池（A：72 基础卡 + 相关无色/诅咒/状态），校验器 + 冒烟全绿。
- **M4 三幕内容**：全怪物/遭遇/Boss/事件/遗物/商店/火堆/宝箱 + 地图生成 + 一局编排 + 存读档 + 战绩。
- **M5 整局闭环**：无头模拟器任意种子完整跑完一局不报引擎错（允许输）；击杀 Boss 的路线用固定种子 + 调试指令发放成型卡组来验证。**bot 智能不是验收项**（建造者决定：否则 M5 会被"造一个会玩尖塔的 AI"静默吞进预算，与研究目标不成比例）。UI 全流程（地图→节点→结算）截图走查。
- **M6 平衡与打磨**：≥1000 局报表、离群卡修复、动画/手感增量（尽力项，范围弹性）。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| wiki 抓取受限或结构变动 | **2026-11-13 已实测解除**：本机直连 wiki.gg / npm registry / Playwright CDN 均可达（仅对话侧 WebFetch 通道受限，项目脚本不走它）。注意 wiki API 需自定义 User-Agent（裸 Python UA 实测 403）。数值真值裁定顺序：wiki 抓取 > 模型知识 > 存疑标注 `verified:false` 待补验；用户可选择性抽检 |
| 基线版本歧义（数值在补丁间有漂移） | P0 钉死补丁号并全文统一，写入文档首节 |
| 原语词汇表中途推翻 | P0 审计前置正是为消灭这条；M2 结束前不启动 M3 灌表 |
| UI 返工吞掉预算（warrior 教训） | 每个里程碑带 Playwright 真实浏览器验收；动画/手感类工作全部压到 M6，不与机制开发混周期 |
| 范围蠕变（"顺手把静默也做了"） | §3 反目标兜底；新增角色需新开设计文档 |
| 平衡调不平 | 忠实抄表优先于调表；离群先查实现 bug 再怀疑数值 |

## 9. 用户已定事项 / 建造者自定事项

**用户已定**：项目性质（个人研究复刻）、路线（B：TS 网页新实现）、代码位置 `warrior_web/`、内容物种类（卡牌+遗物+怪物齐配）。**已裁定**：内容范围 = A 仅铁甲战士（"338 张"经核实为全游戏口径，铁甲实为 72 张——见 §2）。

**建造者决定**（本文档中标注，用户可推翻）：Vite+TS+React+Vitest+Playwright 技术栈；mulberry32；结构化事件流；卡实例模型；里程碑拆分与顺序；中文惯用译名 + 自写简描的文案策略；localStorage 存档；动画从简（CSS/少量 FLIP）；**不继承 warrior 装备槽**（忠实原作优先）；**M5 以引擎闭环为准、bot 强度不设门**；数值真值裁定顺序（wiki > 模型知识 > 标注待验）。
